# Этап 3: сервисная модель «организация → команда → кластер» — тикеты

Цель: на сервере пользователи состоят в командах, кластеры принадлежат командам, а доступ к кластеру и его данным определяется ролью
пользователя в команде-владельце. Данные сервера живут в PostgreSQL (секреты — в зашифрованном виде). Десктоп и личный режим
(`127.0.0.1`) остаются на файловом хранилище с одной неявной организацией и одной командой и не меняют поведения
(раздел 6 плана, ADR-0007, 0008, 0012). Основа — этап 2: у каждой веб-сессии свой вид ядра, поэтому «текущий кластер» известен
`authz` без изменения сигнатур 170 методов `App`.

## Сквозные решения

1. **`authz` берёт кластер из вида сессии.** Для методов, работающих с активным кластером, `authz(perm)` вычисляет роль пользователя
   на `activeCtx` вида: кластер → команда → членство → роль. Методы с явным id кластера (`ConnectToCluster`, `DeleteCluster`,
   `UpdateClusterSettings`, …) передают его в `authz` явно (`authzCluster`). Сигнатуры методов не меняются; `policy_test` расширяется:
   метод либо вызывает `authz`, либо `authzCluster`, либо помечен «вне кластера» (управление командами, профиль).
2. **Чужой кластер = «не найдено».** Вне списка «моих кластеров» методы отвечают как для несуществующего кластера, а не «запрещено».
3. **Два режима хранилища за одним интерфейсом `Store`.** Файловое (десктоп, личный режим) и PostgreSQL (сервис). В файловом — одна
   организация, одна команда, текущий пользователь — её администратор; интерфейс «команды/кластеры по командам» тот же.
4. **Кластеры выносятся из пакетных функций `k8s` (`ListClusters`, `AddClusterFromText`, `GetClusterKubeconfigPath`…) в `ClusterStore`.**
   Сегодня они читают файлы напрямую; без этого владение командой не выразить. Kubeconfig в PostgreSQL хранится только зашифрованным
   (AES-GCM, ключ из `KUBRON_SECRET_KEY`); для client-go он материализуется в памяти (`clientcmd.Load`), а не файлом на диске сервера.
5. **Миграции** — встроенные SQL (`embed`), применяются одной репликой под `pg_advisory_lock`, совместимы назад (этап 4 добавит HA без переделки).

## Порядок

1. **Фундамент:** 3.0 и 3.1a параллельно → 3.1b → 3.1c → 3.1d.
2. **Права:** 3.2 → 3.3 (после них сервис полностью работает через API).
3. **Интерфейс и эксплуатация:** 3.4, 3.5, 3.6 → 3.7 → 3.8 (gate 3).

Каждый шаг мержится отдельно; пока 3.2 не сделан, режим PostgreSQL не рекомендуется для нескольких команд (в `docs/handoff.md`).

## Риски

- **3.0 затрагивает много мест** (`ListClusters`, `GetClusterKubeconfigPath` и др. вызываются из `app`, `k8s`, тестов): делать сначала с файловой реализацией и неизменными тестами.
- **Проверка:** PostgreSQL и client-go у ассистента недоступны — код `store`/`k8s` проверяется у владельца и в CI; чистые части (шифрование, миграционный слой, правила ролей) выносятся в пакеты без внешних зависимостей и тестируются с `-race` на стороне ассистента.
- **Потеря ключа шифрования = потеря секретов** (ADR-0008): процедура резервной копии ключа описывается в `docs/` до выпуска.
- **Общий домашний каталог Helm и журнал операций** остаются общими до этапа 5 (известное ограничение).

## Решения, которые нужны от владельца до начала

1. **PostgreSQL уже в этапе 3** (как в плане, задача 3.1), файловое хранилище остаётся для десктопа и личного режима — по умолчанию да.
2. **Миграции и драйвер:** `pgx/v5` + встроенные SQL-миграции со своим тонким мигратором (без внешней библиотеки миграций) — по умолчанию; альтернатива — `goose`.
3. **Роли при переносе существующих пользователей:** `admin` → org-admin и администратор команды «Default», `operator`/`user` → member и та же роль — по умолчанию.
4. **Ключ шифрования:** из переменной окружения/Secret (`KUBRON_SECRET_KEY`), без KMS; ротация — на этапе 4 — по умолчанию.
5. **PostgreSQL в CI:** service-контейнер `postgres:16` в GitHub Actions (без testcontainers) — по умолчанию.

  `ClusterStatus.health` и `ClusterStatus.error` (причина при плохом состоянии); при изменении состояния всем клиентам уходит `clusters:health`, каждый перечитывает свой список.
  Закрытие у потерявших доступ: раз в 10 с (`Sessions.Views` + `app.EnforceAccess`, вне блокировки реестра сессий) у вида проверяется `CanSeeCluster(активный кластер)`;
  если доступа нет (исключили, перенесли кластер, удалили, отключили) — закрываются терминалы, потоки логов и port-forward вида, активный кластер сбрасывается,
  клиент получает `cluster:access-revoked`. Это же закрывает ограничение из 3.3. UI: красная точка и причина в подсказке значка кластера, тост о потере доступа
  (`cluster.health.*`, `cluster.accessRevoked`, en/ru).
  **Ограничения:** состояние обновляется не чаще интервала (новый кластер сначала «не проверялся»); при недоступной БД > 30 с права отзываются (fail-closed),
  и `EnforceAccess` отключит пользователей от кластеров; informers, запущенные на кластере другого пользователя, не затрагиваются (пул общий, закрывается по idle TTL).

## Требования i18n для всех задач этапа 3

Действуют `docs/i18n.md` и ADR-0014. Для каждой задачи:
- ошибки Go (`errors.New`/`fmt.Errorf` в `internal/`, `pkg/`) — только на английском, с записью в `frontend/src/i18n/locales/{en,ru}/backend.json` (глаголы `%s/%d/%q/%v/%w` → `{p0},{p1}…`);
- тексты интерфейса (экраны «Команды»/«Кластеры», аудит) — ключами в `locales/{en,ru}`, без литералов в шаблонах;
- роли — `roles.*`, действия аудита — `audit.actions.*` (бэкенд отдаёт идентификаторы, не тексты);
- ошибки бэкенда показываются через `errorText(e)`, даты/числа — через `i18n/format.ts`;
- перед коммитом: `node scripts/i18n-check.mjs`, `gofmt -l .`, `go vet ./... && go test ./...`.
