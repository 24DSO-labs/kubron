# ADR-0016: Высокая доступность: две и более реплики kubron-server

- Статус: предложено (ждёт утверждения тимлидом)
- Дата: 2026-10-31
- Связано: ADR-0004, 0005, 0007, 0009, 0012; `docs/tickets/stage-3.md` (3.6); план разработки, разделы 8–10

## Контекст

Сервис работает одной репликой (`replicaCount: 1`). Критерий этапа 4: сервис на двух репликах переживает
потерю одной, а любая реплика обслуживает любой запрос. Что мешает сегодня:

1. `server.Sessions` — карта в памяти. Cookie, выданная репликой A, на реплике B недействительна.
2. Вид сессии (`Session.View`: `auth.Service` с `lastActive`, активный кластер, пул подключений, терминалы,
   port-forward) живёт только в процессе. Его нельзя сериализовать целиком, но и не нужно.
3. `Hub` доставляет события только соединениям своего процесса. Выход, отключение пользователя или отзыв
   доступа, сделанные на реплике A, не закрывают WebSocket и терминалы на реплике B.
4. Реестры терминалов (`termbuf`), логов и port-forward локальные. Запрос к потоку, пришедший на другую
   реплику, сейчас получает «нет такого потока» без объяснения.
5. Блокировка перебора паролей (`auth.shared.failures`) и token bucket (`RateLimiter`) лежат в памяти.
   При двух репликах пароль можно перебирать вдвое быстрее, а при ротации подов счётчики обнуляются.
6. Реплика, получившая SIGTERM, обрывает соединения без предупреждения.

Уже есть: `pgstore.Leader` (`pg_try_advisory_lock`, 3.6) для фоновой проверки кластеров и раздачи статусов
(`cluster_health`), миграции под advisory-lock (`internal/migrate`), доступ и каталог в PostgreSQL.

## Решение

Состояние, от которого зависит правильность (кто вошёл, до какого срока, заблокирован ли логин), — в
PostgreSQL. Состояние, которое можно построить заново (вид ядра, подключения к кластерам, informers,
терминалы), остаётся в памяти реплики и строится лениво. События между репликами — `LISTEN/NOTIFY` как
ускорение; корректность держится на периодической сверке с БД.

### 1. Сессии в PostgreSQL

Таблица `web_sessions` (миграция — следующий свободный номер на момент слияния; `0004` занята Helm):

```
web_sessions
  token_hash        bytea PK        SHA-256 токена из cookie (сам токен не хранится)
  prev_token_hash   bytea NULL      прежний хэш после ротации, действует ещё 30 с (параллельные запросы)
  prev_valid_until  timestamptz NULL
  id                text UNIQUE     публичный id сессии (адресат событий), как сейчас — hex первых 8 байт хэша
  user_id           → users(id) ON DELETE CASCADE
  csrf              text            без cookie не даёт доступа; в API возвращается как и сейчас
  created_at, expires_at            абсолютный срок (KUBRON_SESSION_TTL)
  last_active_at                    последнее действие пользователя в интерфейсе (ReportActivity)
  source            text            адрес клиента при входе (для аудита и блокировок)
  active_cluster_id → clusters(id) ON DELETE SET NULL
  replica_id        text            реплика, создавшая сессию (диагностика, не владение)
```

Что хранится, а что нет:

| В строке | Лениво на реплике (память) |
|---|---|
| пользователь, CSRF, сроки, время последней активности | `View`: `auth.Service` и вид ядра |
| id активного кластера (только идентификатор) | подключение к активному кластеру, informers, кэши |
| адрес клиента | терминалы, логи, port-forward, WebSocket |

**Запрос на любой реплике.** `Sessions.Get(token)`: кэш реплики (ключ — хэш токена, срок записи 2 с) → иначе
`SELECT` из БД. Нашли строку, но вида нет — создаём `NewSessionView`, проставляем пользователя
(`sessionID = user_id`), `lastActive = last_active_at`, а активный кластер подключаем при первом запросе,
которому он нужен (права проверяются как обычно, доступ мог измениться). Пароль и вход повторно не нужны.

**Сроки.**
- Абсолютный: `expires_at`, проверяется при каждом `Get` (в БД и в кэше).
- Простой: настройка ядра `idleTimeoutMinutes` не меняется. Источник истины — `last_active_at`.
  Запись из `ReportActivity` ограничена: не чаще одного обновления за 20 с на сессию (точность простоя —
  минуты). При достижении простоя строка удаляется, событие `session.ended`.
- Фоновая очистка просроченных строк — под `pg_try_advisory_lock` (один исполнитель), раз в минуту.

**Ротация.** Новый токен выдаётся при входе (защита от фиксации сессии) и при смене пароля текущего
пользователя. Остальные сессии пользователя при смене пароля, отключении и удалении удаляются (как сегодня,
`endUserSessionsLocked`). Периодическую ротацию не вводим: cookie `HttpOnly` и ограниченный простой дают
мало, а на нескольких репликах и параллельных запросах она создаёт гонки. Ротация — один `UPDATE`, прежний
хэш живёт 30 с.

**Согласованность кэша.** Кэш до 2 с, плюс сброс записи по событию `session.ended`. Худшая задержка отзыва
сессии без доставленного события — 2 с кэша (дальше сверка). Потерянный `NOTIFY` не оставляет сессию живой.

**Недоступность БД.** Записи в кэше реплики продолжают обслуживаться до 30 с (как fail-closed доступа в 3.6),
затем `503 service_unavailable` без выхода пользователя из системы; восстановление БД не требует повторного
входа.

**Режим одного пользователя и десктоп.** Интерфейс `Store.Sessions()` необязательный (проверка приведением
типа, как `Access()`/`Directory()`). Файловое хранилище его не реализует, и `Sessions` работает на памяти
как сейчас. Поведение десктопа не меняется.

### 2. Какие события нужны между репликами

События ресурсов Kubernetes (pods, deployments и т. д.) рождаются в informers той реплики, где открыт вид
сессии, и между репликами не ходят. Переходят только:

| Событие | Кто публикует | Что делает получатель |
|---|---|---|
| `session.ended {id}` | выход, истечение, вытеснение, отзыв | закрыть WebSocket и потоки сессии, освободить вид, сбросить кэш |
| `user.sessions_ended {user_id}` | отключение, удаление, смена пароля | то же для всех локальных сессий пользователя |
| `access.changed {team_id \| cluster_id \| user_id}` | изменения участников, ролей, команд, привязки кластера | немедленный `EnforceAccess` для затронутых локальных видов (вместо ожидания 10 с) |
| `directory.changed {team_id}` | создание, переименование, удаление команд и кластеров | события `clusters:changed` участникам команды |
| `health.changed {cluster_id}` | лидер проверок после записи в `cluster_health` | прочитать статус из БД и отправить `clusters:health` подписанным сессиям |

Правила:
- Сообщение — `{"v":1,"kind":"…","origin":"<replica_id>", …идентификаторы}`. Только идентификаторы:
  данные получатель читает из БД с проверкой прав так же, как при обычном запросе. Секретов и содержимого
  кластеров в сообщениях нет.
- Своё сообщение реплика отбрасывает по `origin`: локальное действие уже выполнено синхронно.
- Адресация — по `session`, `cluster` или `user` (как в ADR-0009): получатель сопоставляет идентификаторы
  со своими локальными видами и подписками.
- `NOTIFY` отправляется в той же транзакции, что и изменение: доставка по коммиту, откат ничего не рассылает.

### 3. LISTEN/NOTIFY

- Канал `kubron_events`, одно выделенное прямое соединение на реплику (`pgx.Conn`, не из пула).
- Нужно прямое соединение с PostgreSQL: pgbouncer в режиме `transaction` не поддерживает `LISTEN`.
  Для такого случая — `KUBRON_DB_LISTEN_URL` (прямой адрес); без него используется основной.
- Размер полезной нагрузки ограничен ~8000 байт; наши сообщения — десятки байт, при переполнении
  отправитель шлёт укрупнённое событие (`access.changed` для всей организации).
- `NOTIFY` не гарантирует доставку (теряется при обрыве соединения слушателя). Поэтому:
  1. после каждого переподключения слушателя — полная сверка: `Reap` сессий по БД, `EnforceAccess`,
     повторная отправка статусов здоровья;
  2. периодическая сверка раз в 10 с (уже есть для `EnforceAccess`, 3.6) — нижняя граница задержки;
  3. переподключение с экспоненциальной паузой 1–30 с; `/readyz` не падает из-за слушателя, но метрика
     и лог показывают деградацию («события между репликами работают по опросу»).
- Если слушатель не поднялся, сервис работает по опросу: хуже по задержке, не хуже по корректности.

### 4. Реестр потоков и владелец

Потоки (терминал, логи, port-forward) привязаны к процессу, в котором открыт сокет к кластеру. Владелец
кодируется **в самом идентификаторе потока**: `<replica_id>.<случайные 128 бит>`. Таблицы для этого нет:
нет устаревших строк после аварии, нет записи в БД на каждое открытие потока.

- `replica_id` — имя пода (`HOSTNAME`) + случайный суффикс процесса (перезапущенный под с тем же именем —
  уже другой владелец). Задаётся `KUBRON_REPLICA_ID`, по умолчанию строится автоматически.
- Запрос к потоку с префиксом чужой (или несуществующей) реплики → `409`, код `stream_elsewhere`
  (ключ `backend.json`), без проксирования между репликами. Клиент открывает поток заново: терминал —
  новая оболочка с пометкой «соединение восстановлено», логи — подписка заново с текущего момента,
  port-forward — пересоздание.
- Гибель реплики → потоки на ней исчезли → клиент получает обрыв WebSocket, переподключается к живой
  реплике, затем открывает потоки заново. Сессия при этом остаётся действительной (cookie в БД).
- Рекомендация для Ingress: sticky-affinity по cookie уменьшает число таких случаев, но корректность на неё
  не опирается.

### 5. Счётчики входа и ограничения

- **Блокировки по логину** (`auth.shared.failures` по ключу логина) переносятся в PostgreSQL: таблица
  `login_failures(key bytea PK, count, locked_until, last_at)`, ключ — SHA-256 нормализованного логина
  (в том числе несуществующего: нет признака существования пользователя). Обновление — атомарный
  `INSERT … ON CONFLICT DO UPDATE`, проверка блокировки — до проверки пароля. Параметры (5 свободных
  попыток, 15 с → 5 мин) те же. Верхняя граница таблицы 10 000 строк, лишние записи без блокировки
  удаляются при очистке. Обход через разные реплики не работает.
- **Счётчики по адресу клиента и token bucket** остаются в памяти реплики. Это грубое ограничение
  нагрузки, а не защита учётной записи: эффективный лимит — число реплик × порог. Принимаем и записываем в
  `docs/http-security.md`. Перенос в БД дал бы запись на каждый запрос.
- Режим одного пользователя и десктоп — прежние счётчики в памяти (необязательный интерфейс хранилища).

### 6. Фоновые задачи

Всё, что должно выполняться одной репликой, держится под `pg_try_advisory_lock` с собственным ключом:
проверка кластеров (есть, `LeaderKey`), очистка сессий и `login_failures`, хранение аудита. Упавший лидер
отпускает блокировку (закрывается соединение БД), следующая реплика подхватывает работу на ближайшем тике.

### 7. Корректное завершение реплики

`SIGTERM` → состояние `draining` (хук для `/readyz`: новые соединения не направляются на реплику) →
закрытие WebSocket с кодом `1012` (Service Restart) → остановка HTTP-сервера с таймаутом → закрытие пула.
Клиент (`platform/events.web.ts`) при `1012` и при обрыве переподключается с паузой и случайным разбросом
и повторно подписывается на события. Потоки открываются заново (раздел 4).

## Рассмотренные альтернативы

- **Sticky-сессии без общего хранилища.** Не переживает гибель реплики: сессия теряется. Нужна как
  оптимизация, не как основа.
- **JWT без серверного состояния.** Нельзя отозвать (ADR-0004).
- **Redis/NATS для сессий и событий.** Новый компонент в эксплуатации ради нагрузки, которую выдерживает
  PostgreSQL (десятки событий в минуту, сессии — строки). Остаётся запасным вариантом при росте.
- **Только опрос, без `LISTEN/NOTIFY`.** Просто, но отзыв доступа доходил бы за интервал опроса. Берём
  `NOTIFY` как ускорение, опрос — как страховку.
- **Реестр потоков в таблице с `replica_id` и прокси между репликами.** Лишняя запись на каждое открытие,
  устаревшие строки после аварии, сложная маршрутизация потока байтов. Закодированный владелец проще.
- **Периодическая ротация токена.** Мало пользы, множество гонок (раздел 1).
- **Счётчики по IP в PostgreSQL.** Запись на каждый запрос; ограничение остаётся грубым, как и сейчас.

## Последствия

- Каждый запрос веб-API делает не более одного `SELECT` на сессию за 2 с (кэш); запись активности — не чаще
  1 раза в 20 с на сессию. Нагрузочный прогон на 50 сессий проверяет это (`docs/perf-check.md`).
- Для сервисного режима с несколькими репликами обязателен прямой доступ к PostgreSQL для `LISTEN`.
- Потери при гибели реплики: открытые терминалы, логи и port-forward (открываются заново). Входы и
  настройки не теряются.
- Новые необязательные интерфейсы хранилища: `Sessions()`, `LoginFailures()`. Файловое хранилище и режим
  одного пользователя не меняются.
- Новые ключи `backend.json` (en, ru, cn): `stream_elsewhere`, `service_unavailable` и т. п.
- План: PR 2 — идентичность реплики и завершение; PR 3 — сессии в PG; PR 4 — события; PR 5 — потоки,
  блокировки входа, фоновые задачи; PR 6 — чарт и e2e `e2e-ha`.
